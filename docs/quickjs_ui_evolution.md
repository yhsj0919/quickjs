# quickjs_ui 演进方向

## 1. 定位

`quickjs_ui` 的目标是成为 Flutter 应用中可嵌入的、Flutter-native、Schema-driven、
QuickJS-powered 动态页面运行时。Flutter 始终是应用主体，负责应用启动、导航、全局状态、
布局绘制、输入、无障碍和原生能力；JavaScript 只负责单个 JSUI 页面或局部区域的状态、事件
和业务控制流。两端只通过可校验、可序列化的协议通信。

项目不与 WebF 竞争浏览器兼容性，也不追求把全部 Flutter API 暴露给 JavaScript。核心价值是：

- 页面能力由宿主显式授权，远程代码默认不拥有网络、存储、文件和导航能力。
- UI Schema 可做版本校验、大小限制、快照、诊断和兼容处理。
- 常用组件保持 Flutter 风格命名，让小列表和大列表、静态页面和动态页面使用一致的公开写法。
- 复杂原生能力通过组件注册表和 host capability 扩展，不扩大默认攻击面。

### 产品边界

JSUI 可以作为 Flutter 导航栈中的完整页面，也可以作为 `QuickjsUiView` 嵌入原生页面的一块
区域；同一页面可以同时包含宿主 Flutter Widget、JSUI Schema 组件和注册的原生扩展组件。
它的加载、更新、页面包和 Bridge 体验类似 Web，但渲染仍由 Flutter 完成。

这与 MXFlutter 的目标有本质区别：MXFlutter 让 TypeScript/JavaScript 成为应用主体，并在
JS 中模拟 Flutter Widget Tree、State、`build()` 和 `setState()`；`quickjs_ui` 不复制完整
Flutter 应用模型，只为原生 Flutter 应用补充动态页面能力。因此不需要覆盖全部 Widget、
Controller、导航和全局状态，也不应让一个 JS Session 的故障扩散到整个应用。

## 2. 目标运行模型

```text
JavaScript 页面逻辑
        │
        ├── 首次加载：完整 UI Schema
        ├── 普通更新：状态提交 / 按需启用局部 Patch
        └── 大数据组件：List/Grid 专用按需数据通道
        │
Schema 校验、权限检查、版本兼容、更新批处理
        │
Flutter 原生 Widget、RenderObject 和宿主组件
```

完整 Schema、可选局部 Patch 和列表 Builder 是同一套协议的不同传输粒度，不应演变成相互
冲突的页面写法。普通数量也允许使用 Builder；数据规模增长时不需要改写页面的状态和事件模型。

## 3. 第一阶段：稳定当前基线

目标是让现有全量 Schema 模式可预测，并为后续增量更新建立测量基线。

- 固化页面、事件、生命周期、资源和错误协议的版本号及兼容策略。
- 给单次结构化值转换增加可诊断的节点数、深度、字节数和耗时指标。
- 保留完整 Schema 作为首次渲染、低频页面和调试快照的标准格式。
- ListView/GridView 使用按需 Builder 与批量预加载，避免把超大 item 图一次性跨 JS/Dart 边界传输。
- 分页加载、下拉刷新和纯超长列表保持能力分离；未声明回调时默认关闭对应行为。
- 建立首屏时间、滚动帧耗时、JS/Dart 转换量、缓存命中率和内存峰值基准。

完成标准：超大列表不再因完整对象图转换失败；快速滚动、分页追加和刷新不会错误替换已有数据
或跳回旧索引；同一套公开写法覆盖少量和大量 item。

## 4. 第二阶段：原生混合与页面隔离

这一阶段优先巩固“Flutter 主体、JSUI 补充”的产品边界：

- 原生页面和 JSUI 页面可相互导航，但最终路由解析、权限检查和返回行为由 Flutter 宿主决定。
- `QuickjsUiView` 可稳定嵌入任意原生布局，并正确同步 show/hide、前后台和 dispose 生命周期。
- 宿主组件注册表支持在 JSUI 中使用地图、视频等原生能力，JS 不持有其 Controller 或原生对象。
- 每个页面 Session 独立设置内存、超时、资源、权限和错误边界；加载失败可显示原生兜底页面。
- JSUI 页面只管理局部状态；登录态、账户、支付等应用状态由宿主通过 props/capability 提供。
- 动态包异常时支持回退内置版本，单页失败不得破坏 Flutter 导航栈和其他页面。

完成标准：独立 JSUI 页面、原生页面内嵌 JSUI 区域以及 JSUI/原生组件混合三种形式使用同一套
页面协议；销毁页面后不残留 runtime、回调、异步请求或原生组件资源。

## 5. 按需引入批量调度与局部 Patch

完整重建简单可靠，也符合动态页面的主要使用场景。只有性能数据证明高频、小范围更新成为通用
瓶颈时，才增加受控 Patch 协议；它是页面传输优化，不是为了实现虚拟 DOM 或完整 JS 应用框架。
全量 Schema 始终作为首次加载、降级和校验基线。

建议支持的最小操作包括：

- 更新指定稳定 key 节点的 props。
- 插入、删除、替换和移动指定父节点的 children。
- 向 List/Grid 追加、替换或删除数据区间。
- 事务提交：同一事件循环内的多次修改合并到一个 Flutter frame。
- revision 校验：旧异步结果不能覆盖更新的页面状态。

Patch 必须满足以下约束：

- 目标由稳定 key 和 revision 确定，禁止依赖易变化的可视索引作为唯一身份。
- Patch 经过与完整 Schema 相同的类型、权限、大小和组件白名单校验。
- Patch 失败时给出结构化错误；开发模式可退回完整 build，生产模式不得静默产生半更新 UI。
- Inspector 能还原 Patch 前后状态，并记录来源 action、耗时和受影响节点数。

完成标准：计数器、表单局部输入、分页追加等常见操作不需要跨边界传输整棵 UI 树；连续更新在
一帧内合并，页面状态仍可通过完整快照复现。

## 6. 专用高性能组件通道

列表、网格、图表、地图、视频和富文本编辑器不适合仅靠通用树协议承载。它们应继续保持普通
组件的声明式入口，但内部使用专用数据和生命周期通道。

列表与网格优先完善：

- 按索引区间批量请求 item，支持固定数量预加载，不强制业务提供精确 item 高度。
- 高度参数只作为可选估算值，用于优化滚动范围和首屏计算，不能成为正确性前提。
- 缓存按稳定 item key、数据 revision 和模板 revision 失效，不能仅按 index 缓存。
- 分页请求具有 request id、页游标、去重、过期结果丢弃和并发保护。
- 加载更多允许显示 footer、overlay 或宿主提示；提示是否可见不影响请求状态机。
- RefreshIndicator 作为显式包裹组件，避免普通快速上滑被解释为刷新。

其他复杂组件通过 `QuickjsUiComponentRegistry` 接入；JS 只持有可序列化 props、事件描述和资源
标识，不持有 Dart Widget、Controller 或原生对象。

## 7. 开发工具和类型系统

- 从 Schema、组件注册信息和 host capability 生成 TypeScript 定义。
- 开发期检查未知组件、未知属性、错误事件载荷和不兼容协议版本。
- Inspector 展示 JS 状态、Schema/Patch、Widget 映射、列表窗口、缓存和异步请求时间线。
- 支持状态保留热重载、资源图查看、慢 build/Patch 告警和可导出的复现快照。
- 建立协议 conformance tests，使宿主自定义组件可以验证生命周期和错误行为。

完成标准：页面开发者不需要理解 JS/Dart Bridge 的实现细节，也能定位一次更新为什么发生、更新
了哪些节点以及耗时在哪里。

## 8. 发布安全与生产治理

- 页面包签名或可信来源校验、checksum、版本约束和可回滚缓存。
- origin allowlist、权限清单、资源大小限制、运行时间限制和内存限制。
- capability 按页面包和路由授予，默认最小权限；资源访问权与宿主 API 权限相互独立。
- 灰度、回滚、失效开关和最低宿主版本策略由发布系统负责，运行时只执行可验证策略。
- 记录包版本、协议版本、宿主版本和关键错误，支持生产问题关联到准确页面产物。

动态下发能力需要由应用发行方结合目标平台审核规则评估。本项目只提供技术边界，不把代码混淆
或资源加密视为安全授权机制。

## 9. 明确不做

- 不实现 DOM、CSSOM、HTML Parser、完整 CSS 布局或浏览器兼容层。
- 不以直接运行 React、Vue、Svelte 应用为目标；该场景优先评估 WebF。
- 不让 JavaScript 成为应用主体，不在 JS 中重建完整 Flutter 应用、导航和全局状态模型。
- 不全量映射 Flutter Widget 和 Dart API，只维护经过选择的稳定 Schema 子集。
- 不允许 JavaScript 直接创建、保存或操作 Flutter Widget、Controller 和 RenderObject。
- 不默认开放网络、存储、文件系统、导航和设备敏感能力。
- 不用全量对象树无限扩容代替按需构建，也不用局部 Patch 取代首次完整 Schema。
- 不把 Shorebird 一类编译补丁方案纳入页面协议；两者可以组合，但解决的问题不同。

## 10. 建议优先级

1. 稳定页面 Session、原生混合、导航互通、异常隔离和资源回收。
2. 稳定 Builder、分页、刷新隔离、revision 和性能基线。
3. 完善列表/网格专用通道和 Inspector 可观测性。
4. 只有通用性能数据需要时，再设计最小 Patch 协议及帧内批处理，不追求虚拟 DOM。
5. 生成组件及 host API 类型，建立第三方组件一致性测试。
6. 最后补生产签名、灰度、回滚和平台治理集成。

这条路线保留了 Schema 驱动方案的可控性，同时吸收 WebF 的批量更新、脏区思想和专用列表能力，
但避免承担完整 Web 平台兼容成本。
