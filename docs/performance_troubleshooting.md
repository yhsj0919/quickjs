# 性能问题诊断与重构流程

本文规定 QuickJS、quickjs_ui、示例页面和插件发生卡顿、掉帧、高负载、拖影或输入干扰时的统一处理流程。性能修改必须先得到可复现、可比较的数据，不允许先降低效果或叠加局部补丁再反推原因。

## 强制顺序

所有性能问题按以下顺序处理：

1. 开启性能检测。
2. 建立原生基线。
3. 对页面进行分层排除。
4. 用单变量对照确定根因。
5. 在拥有问题的架构边界重构。
6. 删除失败实验、临时分支和被替代的旧路径。
7. 使用相同环境复测并完成回归测试。

没有完成前四步，不应修改生产效果、降低素材质量、减少动画数量或调整默认帧率。

## 1. 开启可比较的性能检测

性能结论必须来自 Profile 或 Release 构建。Debug 数据只能用于发现明显异常，不能作为优化验收结果。

诊断面板至少显示：

- 运行模式：`DEBUG`、`PROFILE` 或 `RELEASE`。
- 实际 FPS、屏幕刷新率和单帧预算。
- UI、Raster、Total 的均值、P90 和最大值。
- 样本数和超预算比例。
- 逻辑尺寸、物理尺寸和 DPR。
- 鼠标或指针输入频率。

统一采样要求：

- 每组至少收集 180 帧。
- 截图前保持鼠标和触摸输入为 0。
- 使用同一台设备、相同分辨率、DPR、天气或业务数据。
- 对静态页面使用独立且极小的原生帧驱动器持续请求 VSync；驱动器必须拥有自己的最外层重绘边界，不能把重绘传播到被测页面。
- 暂停动画后没有持续帧请求时，FPS 表示“产生了多少帧”，不表示设备的最大渲染能力。
- Web 页面能够绘制但动画停在一帧时，先检查浏览器控制台中的
  `matchMedia('(prefers-reduced-motion: reduce)').matches`，以及性能快照中的
  `reducedMotion`、`quality` 和 `stoppedCanvasTickerCount`。系统请求减少动画时，
  JSUI 会主动停止 Canvas Ticker，不能将其误判为 Web Canvas 或 VSync 故障。

## 2. 建立原生基线

先移除 QuickJS 页面，只保留与正式测试相同的 Flutter 宿主、诊断面板和帧驱动器。记录原生基线：

| 场景 | FPS | UI avg/P90 | Raster avg/P90 | Total avg/P90 |
| --- | ---: | ---: | ---: | ---: |
| 原生基线 |  |  |  |  |

如果原生基线已经超过帧预算，先排查设备、Flutter 渲染后端、分辨率、DPR、系统合成和运行模式。此时不能把全部问题归因于 QuickJS 页面。

## 3. 分层排除

从页面最外层开始二分，每次只改变一个变量。动画页面推荐至少提供以下诊断场景：

1. 原生基线。
2. 仅背景。
3. 仅内容。
4. 完整页面。

内容仍然昂贵时继续拆分，例如：

- 标题区与数据区。
- 列表、图表和指标卡片。
- 图片、SVG、文字和透明效果。
- 静态层与动态层。
- Canvas、普通 Widget、图片粒子和平台视图。

分层模式必须尽量保持相同的布局尺寸、数据、帧驱动和采样时间。移除图标时应保留同尺寸占位，避免把布局变化误判为图标收益。

## 4. 用数据确认根因

记录各层相对原生基线的增量，而不只比较 FPS：

```text
层开销 = 当前场景 Raster 均值 - 原生基线 Raster 均值
```

只有满足以下条件，才能把某模块认定为主要根因：

- 移除该模块后，Raster 或 UI 耗时稳定、显著下降。
- 保留其他布局和采样条件后，下降仍可复现。
- 恢复该模块后，耗时重新出现。
- P90 与均值方向一致，不是单次冷启动尖峰。

一次无收益的修改必须撤回。不能保留“理论上可能有效”但实机数据没有改善的边界、缓存或调度补丁。

### 示例：SVG 根因确认

一次天气页面排查得到：

- 原生/仅背景 Raster 约 22–23ms。
- 完整静态内容 Raster 约 44–45ms。
- 保持布局不变、只移除约 15 个 SVG 后，Raster 回到约 23–24ms。

因此根因是固定尺寸 SVG 仍使用逐帧矢量 `picture` 绘制，而不是天气背景动画、读秒、鼠标事件或透明卡片。正确修复边界是通用 `Svg` 媒体组件的渲染策略，而不是在天气页面逐个替换图标。

## 5. 选择正确的修复边界

优先级如下：

1. 通用组件或渲染协议存在错误：修复 core/renderer。
2. 插件生命周期、资源所有权或缓存边界错误：重构插件。
3. 独立业务模块设计错误：重构模块。
4. 只有某个示例参数不合理：调整示例。

满足以下任一情况时，应优先重构而不是打补丁：

- 同类问题会影响多个页面或天气类型。
- 页面正在弥补底层组件缺失的缓存、生命周期或调度能力。
- 修复需要多个兼容分支、重复监听器或额外定时器。
- 已经出现“修一个场景、另一个场景继续复现”的情况。

修改 core 前必须说明原因、范围和可能影响。重构完成后应删除页面特判、旧实现、临时兼容层和无收益实验。

## 6. 验收

性能修复至少完成以下验证：

- 在相同设备和场景记录修改前后的均值、P90、最大值和超预算比例。
- 冷启动后等待缓存稳定，再记录稳态数据；必要时同时报告首次加载成本。
- 测试动画开启/关闭、页面隔离/恢复、窗口缩放、路由退出和重新进入。
- 测试鼠标移动、滚轮、触摸和高频输入不会抢占动画调度。
- 验证暂停、dispose 和路由离开后没有残留 ticker、timer、listener 或 QuickJS 会话。
- 运行相关单元测试、Widget 测试、Schema 校验和静态分析。

最终报告使用以下模板：

```text
环境：设备 / 构建模式 / 分辨率 / DPR / 刷新率
基线：UI、Raster、Total avg/P90
分层结果：仅背景 / 仅内容 / 子模块 / 完整页面
根因：由哪组单变量对照确认
修复边界：core / renderer / plugin / module / demo
结构变化：删除了哪些旧路径或临时方案
结果：修改前后数据
验证：测试、生命周期和交互场景
```

## 禁止做法

- 在没有基线时直接减少粒子、降低 FPS 或压缩素材。
- 用 Debug 数据宣称 Release 性能结论。
- 同时修改素材、动画数量、透明度和布局后比较结果。
- 把静态页面没有请求帧时的低 FPS 当成性能下降。
- 在页面内长期保留为底层缺陷兜底的定时器、重复缓存或重绘补丁。
- 实机无收益后仍保留实验性修改。
- 只优化平均值而忽略 P90、最大值和可见连续掉帧。
