# 虚拟列表与同步 builder 基准

独立入口：`examples/lemon_js_example/lib/list_runtime_benchmark.dart`。
这是基准专用同步 builder 适配器，生产 `ListView.builder` 批次协议尚未更改。

在 example 目录构建：

```powershell
flutter build windows --release --no-pub --target lib/list_runtime_benchmark.dart
```

运行生成的 exe，第一参数可指定 JSON 输出的绝对路径。程序完成两轮后退出。
每轮包含原生 Flutter、Dart schema、同步 JS builder、现有虚拟列表本地执行、现有虚拟列表 worker 执行。
第二轮反转顺序，避免固定测试顺序偏差。

十万条 `Item N` 文本，行高 48，逻辑视口 800×600，缓存 250，虚拟列表批次 20。
同一 Ticker 每 vsync 滚动 8 逻辑像素，预热 60 帧，驱动 480 个采样 tick（实际渲染帧数单独记录）。
记录 FrameTiming 的 UI / Raster / Total 平均、P90、最大值、超预算帧数，显示器刷新率、DPR、物理窗口大小、实际滚动距离和边界受限帧数。
每组至少 180 个真实帧样本，否则程序报告错误。

`rowCallsIncludingWarmup` / `rowBuildTotalMs` 包含预热；虚拟列表使用 `rangeEvents` 记录范围请求，不将其与同步行调用次数直接比较。
同步 builder 每行经过 JS 值转换、节点解析和现有 renderer；Dart schema 保留相同解析和 renderer，以区分 JS 桥成本。
同步 builder 不额外缓存已建 Widget；现有虚拟列表沿用生产缓存策略。
两种列表的总长度和随机跳转语义不同；若实际滚动距离不同或出现边界受限帧，不能只按帧耗时评价胜负。

此基准测连续滚动，不代表复杂业务行、网络加载、更新已有行、随机跳转或内存峰值。

## 调用优化前基线（2026-10-11）

Windows Release，Impeller OpenGLES，显示器报告 75 Hz，帧预算 13.333 ms。
物理窗口 1582×853，DPR 1.25，实际逻辑视口 800×600。
同一机器连续运行两轮，第二轮反转顺序。每组每轮 430～480 帧左右，最低 432 帧的虚拟本地组及最低 430 帧的 Dart schema 组均满足最低 180 帧要求。
完整逐轮指标见 [原始 JSON](list_runtime_benchmark_results.json)。

下表平均值按帧样本数加权；P90 是两轮各自的值范围，并非合并分布的 P90。单位 ms。

| 模式 | 样本总数 | UI 平均 | UI P90 范围 | UI 最大 | Raster 平均 | Total 平均 | UI 超预算帧 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 原生 Flutter | 960 | 0.245 | 0.329～0.391 | 1.041 | 0.711 | 1.962 | 0 |
| Dart schema + renderer | 910 | 0.235 | 0.347～0.355 | 0.700 | 0.681 | 1.992 | 0 |
| 同步 JS builder | 918 | 0.388 | 1.213～1.219 | 2.000 | 0.710 | 2.119 | 0 |
| 现有虚拟列表 / 本地执行 | 881 | 0.225 | 0.309～0.318 | 0.568 | 0.666 | 1.909 | 0 |
| 现有虚拟列表 / worker | 885 | 0.238 | 0.314～0.351 | 0.646 | 0.695 | 1.995 | 0 |

各组每轮实际测量滚动距离均为 3840 逻辑像素，边界受限帧均为 0。
所有组的 UI 和 Raster 超预算帧均为 0。Total 指标中 worker 虚拟列表第二轮有 1 帧超过预算（20.740 ms）；其他组 Total 超预算帧均为 0。Total 包含等待阶段，不能将这一帧直接归因为 JS 执行。
渲染帧吞吐估计为原生 79.85～80.75、Dart schema 71.88～83.30、同步 builder 75.42～83.38、虚拟本地 73.02～83.47、虚拟 worker 75.01～77.90 帧/秒。
这是 engine FrameTiming 样本数除以采样墙钟时间，表示渲染帧吞吐估计，不是显示器实际呈现 FPS；部分值超过系统报告的 75 Hz，不能据此宣称屏幕以更高刷新率显示，也不宜按这些小幅差异排名。
帧时间戳过滤采样窗口，允许窗口结束后接收延迟送达的 timing 批次，避免按回调送达时刻混入预热帧。

同步 builder 每轮调用 108 次（含预热），整条行生成链累计 89.446 / 90.299 ms，平均约 0.832 ms/行。
Dart schema 同样 108 次，累计 3.502 / 3.577 ms，平均约 0.033 ms/行。
原生行生成约 0.0026 ms/行。上述行生成不包含 Flutter 后续 layout / paint，不能当成完整行渲染成本。
现有虚拟列表每轮请求 5 个后续范围，每批 20 行，沿用生产批次与 Widget 缓存策略。

结果说明：简单文本行的持续滚动中，同步逐行 JS 调用比批次虚拟列表多消耗约 0.163 ms UI 时间/帧，UI P90 也更高，但本机两者都没有 UI 超预算帧。
同步组与 Dart schema 组的单变量对照将额外开销定位到逐行 JS 调用及值转换路径，尚未进一步分离 JS 编译、执行和 wire 转换的占比。
虚拟本地与 worker 的差异较小，两轮仍有环境波动，不据此认定某一执行模式普遍更快。
同步 builder 的价值是可以遵循 Flutter 的即时按需构建规律，并可访问完整 itemCount；本次数据不支持“同步一定比批次更快”的结论。

基准采用同一个最小宿主，虚拟组直接连接生产 `JsUiSession`、节点 renderer 和列表 Widget；不包含应用 `JsUiView`/Controller 的全部外层调度成本。
此次仅新增基准入口与报告，未针对测量结果修改生产列表策略。

## item 复用与内存补测

入口 `examples/lemon_js_example/lib/list_retention_benchmark.dart`。构建时将 target 改为这个文件。
运行 exe 时传入两个参数：`native` / `sync-builder` / `virtual-local`，以及 JSON 输出绝对路径。
每个模式必须独立启动进程；同时运行多个基准会影响内存和帧驱动，不应合并比较。

使用相同的 Stateful 行探针，十万行、行高 48、cacheExtent 250、视口 800×600。
场景为向下 480 行、回到顶部、再向下 960 行，每个 tick 移动一行。
记录 Widget 创建数量与重复 index 创建数量，State mount / dispose / update / build，存活和峰值 State 数、挂载 Element 数、范围事件及缓存行数。
虚拟组的 `cachedRowWidgets` 根据连续已加载 batchEnd 推导：生产 `_items` 按 index 累积保存 Widget，reset 或页面销毁才清空；该指标不是强制 GC 后的堆对象普查。

复用须区分 Widget 描述复用与 Element/State 存活。缓存同一个 Widget 后回滚，仍可能创建新的 Element/State。
默认探针未请求 keepAlive，不引入跨 index 的 State 池。三组的生命周期探针和统计开销一致。
统计用的 index 计数表会持有访问过的 index，但不会持有行 Widget 或 State；RSS 包含这部分相同的测量开销。

内存指标是 OS 进程当前 RSS 和整个进程生命周期峰值 RSS，分别包含 Dart、QuickJS、Flutter/native 分配及分配器保留的页，不能当成 Dart retained heap。
Release 未强制 GC；页面释放后 RSS 不下降不能单独证明内存泄漏。
RSS 初始值可能因进程启动和图形分配发生变化，应优先比较同进程各阶段增量、两轮趋势以及缓存/存活对象计数，不能只按跨进程绝对 RSS 排名。

### 调用优化前的补测结果（2026-10-11，两轮独立进程）

完整数据见 [item 复用与内存 JSON](list_retention_benchmark_results.json)。第二轮反转三种模式的执行顺序。
六个进程均完成相同路径：23040 px 向下、23040 px 回到顶部、46080 px 向下，边界受限 tick 均为 0。
页面释放后行 State 均为 0，mount 和 dispose 数量一致。

| 模式 | 返回顶部新增行 Widget | 返回顶部新增行 State | 峰值存活行 State | 扩展至 960 行后的手动缓存行 Widget | 累计创建行 Widget |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原生 Flutter | 474 | 474 | 25 | 0 | 1932 |
| 同步 JS builder | 474 | 474 | 25 | 0 | 1932 |
| 现有虚拟列表 | 0 | 474 | 25 | 1000 | 1000 |

计数两轮相同。初始存活 State 为 18，向下滚动后的稳定值为 24，峰值 25。
“手动缓存 0”只表示没有跨滚动历史保存行 Widget 的业务 Map，不代表 Flutter 视口/cacheExtent 内没有存活 Widget。
现有虚拟列表初始保存 40 个行 Widget，向下 480 行后保存 520 个，回到顶部仍为 520 个，向下 960 行后为 1000 个。
它确实减少了重复 JS/schema/Widget 构建，但不会因此保留已经离屏的 State；相同 Widget 再次进入 sliver 时会重新创建 Element/State。
本例没有请求 keepAlive，也没有实现跨 index 的 Element/State 池。一般业务的焦点、编辑状态或显式 keepAlive 会改变存活量，不能将此计数推广到所有行组件。

下面是相对各自进程初始阶段的 RSS 增量，单位 MiB；列内两个值对应两轮，未强制 GC。

| 模式 | 向下 480 行 | 回到顶部 | 向下 960 行 | 释放页面后 |
| --- | ---: | ---: | ---: | ---: |
| 原生 Flutter | 3.738 / 4.043 | 3.555 / 4.281 | 4.281 / 4.602 | 4.285 / 4.703 |
| 同步 JS builder | 4.250 / 4.547 | 4.910 / 5.180 | 5.395 / 5.488 | 3.660 / 4.113 |
| 现有虚拟列表 | 5.266 / 4.488 | 4.324 / 3.527 | 4.867 / 4.020 | 4.867 / 4.020 |

各进程初始 RSS 为 138.496～162.945 MiB，说明跨进程绝对值存在显著启动分配波动。
同步模式最终 RSS 增量略高于虚拟列表，不能依据“没有历史 Widget Map”直接宣称当前同步适配器更省实际进程内存。
RSS 会受到反复创建、JS 值转换、GC 时机和分配器保留页等因素影响；本次未分离它们的贡献，也未测量 full GC 后的 retained heap。
缓存数量的增长趋势则是明确的：当前虚拟列表保留量跟随历史已加载 index 数增长，回滚不会淘汰；默认同步 builder 的行 State/Element 存活量跟随视口与 cacheExtent。

因此要同时考虑三个维度：单次构建成本、回滚时避免重复构建的收益、长期缓存的上限。
后续生产同步 builder 的缓存应有明确容量与失效规则，并把需要保存的业务状态和 keepAlive 策略单独定义。
不能为了复用而跨不同 item 随意保留旧 State；也不能用无限历史 Widget 缓存来换取所有回滚都不重建。
此次补测没有修改生产缓存或 keepAlive 行为。

## 核心直接调用优化后复测（2026-10-11）

用相同 Release 列表入口、相同数据与行组件、相同视口/缓存/滚动驱动跑两轮，第二轮反转顺序。
本次核心改动在原生采用已安装调用器的 `JS_Call`，共享参数/结果编解码器，缓存 native 宿主回调 codec；没有改变生产列表缓存。
完整数据见 [优化后 JSON](list_runtime_benchmark_after_invocation.json)，其中还包含复用的纯调用 CPU 基准结果。

| 模式 | 帧样本数 | UI 平均 ms | UI P90 范围 ms | UI 最大 ms | Raster 平均 ms | Total 平均 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原生 Flutter | 957 | 0.236 | 0.327～0.375 | 0.673 | 0.684 | 1.917 |
| Dart schema + renderer | 929 | 0.236 | 0.353～0.354 | 0.742 | 0.676 | 1.892 |
| 同步 JS builder | 960 | 0.253 | 0.460～0.477 | 1.025 | 0.669 | 1.925 |
| 现有虚拟列表 / 本地执行 | 960 | 0.228 | 0.313～0.322 | 0.870 | 0.666 | 1.882 |
| 现有虚拟列表 / worker | 959 | 0.224 | 0.305～0.321 | 0.585 | 0.659 | 1.883 |

每组每轮至少 449 个真实帧样本；平均按样本数加权，P90 范围是逐轮值。
本轮所有组 UI / Raster / Total 超预算帧均为 0，滚动距离均为 3840 px，边界受限帧为 0。
同步 builder 两轮均构建 108 行（含预热），完整行生成链累计 16.835 / 15.460 ms，
平均约 0.150 ms/行；优化前为 89.446 / 90.299 ms，平均约 0.832 ms/行，约快 5.6 倍。
其 UI 平均从 0.388 ms/帧降至 0.253 ms/帧，P90 从约 1.21 ms 降至约 0.46～0.48 ms。
同期原生行生成约 0.003 ms/行，Dart schema + renderer 约 0.036 ms/行。

纯调用基准的 23.49 μs/行来自持续预热后的 1000 行循环；完整列表计时包含解析与 renderer，且调用随滚动间隔发生。
两种计时场景不同，不能用纯调用数值直接代替真实 UI 行生成耗时，也没有进一步测出剩余开销各层的准确占比。
此次没有复测 full GC 后堆内存或 RSS。上面的 item 复用/RSS 表属于优化前基线；缓存策略未改，不能据它推断优化后进程内存变化。
原生与同步 builder 仍不等价：同步方案还有参数与 schema 转换；批量方案仍可摊薄边界成本，但当前帧时间差异已经较小。
